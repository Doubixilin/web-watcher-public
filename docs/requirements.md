# Web Watcher 产品需求

日期：2026 年 10 月 6 日

## 使用场景

远程控制一台 Mac 时，可能遇到 Wi-Fi 突然断开，也可能遇到无线关联仍然存在但上游无法访问互联网的情况。只观察 Wi-Fi 是否连接，不能判断远程主机是否仍然可达。

用户希望建立本机软件：既能在适当条件下切换到备用网络，也能持续检测不同网站的连通性和网络健康，查看历史与故障原因。

主、备用网络由使用者在本机配置并验证。真实名称、网卡和代理快照不进入公开源码或提交历史。

## 已确认需求

- 使用有界面的本机软件，提供菜单栏入口与主窗口。
- 支持监测多个网站、服务或用户自定义目标。
- 支持网络健康观测，不能只显示 Wi-Fi 是否连接。
- 主网络上游断网但 Wi-Fi 仍连接时，能够识别异常并按策略尝试备用网络。
- 面向当前 Mac 的研究与开发，配置和历史优先保存在本机。

技术栈已采用原生 SwiftUI / AppKit。完整界面布局、自动恢复默认开关和具体阈值属于实现选择，尚未由用户确认。

用户本轮追加并授权开发：读取正式当前 Wi-Fi 名称；观察无线信号与质量；识别当前连接的 Wi-Fi 代际；区分链路速率、实际流量与公网带宽；显示主、备用候选；优化界面并增加图表；按需显示进程收发；菜单栏可选择网速显示。当前实现和验收边界见 [会话交接](HANDOFF.md)。

## 第一版能力

| 部分 | 目标 |
| --- | --- |
| 网络总览 | 显示当前接口、网络状态、网关、DNS、代理路径及最近一次检测结果 |
| 网站监测 | 配置目标、协议、路径、检测周期、超时与预期结果，展示失败发生在哪一层 |
| 网络健康 | 分别观察延迟、ICMP 丢包、抖动、HTTP 请求失败率、DNS 延迟；权限允许时显示 Wi-Fi 信号信息 |
| 故障历史 | 保存开始、恢复、持续时间、网络环境和检测证据；提供时间筛选与导出 |
| 网络恢复 | 指定候选网络、选择手动或自动模式，展示切换原因、进度、验证和失败结果 |

完整测速由用户主动触发。本轮增加按需读取系统进程统计与手动刷新附近 Wi-Fi；不进行全流量抓包。第一版仍不要求持续测速、局域网设备扫描、云端平台或跨平台实现。

## 检测语义

同一个检测目标需要区分以下结论：DNS 是否解析成功、TCP 是否建立、TLS 是否成功、HTTP 是否得到响应、响应是否满足业务条件。响应时间应标明测量阶段，无法测得的阶段不要用其他数字替代。

例如，一个业务接口返回 HTTP 422，说明可以与服务器交换 HTTP 响应，但不证明业务已登录、功能正常或远程控制会话已恢复。它也不能直接被解释为本机没有互联网。

ICMP 目标不响应可能来自策略限制。多个检测目标应来自独立服务，并使用适合现场网络的协议；国内、国外和代理目标分别展示，不能只凭一个国外站点判断出口失效。

## 恢复策略

自动切换必须由网络层面的连续证据触发。网站自身故障、证书问题、HTTP 错误或代理节点异常应分别呈现，不能都归结为上游断网。

0.3.0 已采用独立恢复检测：无线链路每 2 秒复核，持续断开去抖；仍关联时每 10 秒探测 3 个无线 TCP 目标，连续 2 轮全失败才尝试切换。自动恢复初始关闭，具体等待、冷却与验收结果见 [会话交接](HANDOFF.md)。这些是实现默认值，实际连接 / 恢复时长尚待实测，不是承诺。

切换后应等待网络配置就绪，再验证公网和关键服务路径。备用网络失败时不能仅凭切换命令退出码标记成功。恢复后保持在可用网络，设置冷却时间，避免反复切换；原网络与其他候选仍应能够在后续失败时被重新尝试。

一张普通 Wi-Fi 网卡通常只能关联一个网络，不能假设在备用网络上可以同时无扰动验证原网络。自动切回主网络属于后续独立策略。

## 验收要求

1. 窗口关闭后监测继续运行，菜单栏仍能显示状态；明确退出软件与关闭窗口的区别。
2. 单个网站宕机、HTTP 错误、ICMP 被限制、代理单独失败时，不误触发 Wi-Fi 切换。
3. 能通过模拟数据验证“Wi-Fi 已连接但上游不可达”的检测、连续失败、恢复和冷却行为。
4. 实际网络验收中，后台和锁屏状态下无需临时密码弹窗即可完成被授权的切换。
5. 切换后验证公网连接；远程控制是否真正恢复需单独观察实际会话，不能用服务器可达代替。
6. 重启、登录启动、休眠与唤醒的支持范围有明确说明，权限缺失时清楚显示能力受限。
7. 网络故障期间，日志和检测历史仍能在本机保存，且不记录凭据。
8. 首次持续运行测试记录实际 CPU、内存、探测流量和存储增长，再确定默认频率与保留周期。

实际断网与切网验收应安排在有回退保障的维护窗口，避免将唯一远程控制路径当作无保护的测试对象。
